# RFP Answer Skill

Four-mode skill for turning a customer RFP document into a structured, professional proposal response — grounded in real commercetools capabilities and your company's reference material.

```
/commercetools-rfp init       → drop RFP_CONFIG.md and folder structure templates
/commercetools-rfp analyze    → read the RFP document, extract and score requirements
/commercetools-rfp generate   → produce the full proposal response document
/commercetools-rfp review     → check completeness, flag unaddressed requirements
```

Run `init` once to set up configuration. Fill in `RFP_CONFIG.md` with your company profile, capabilities, and team. Then run `analyze` on the customer's RFP, followed by `generate` to produce the response.

---

## Mode: init

**When**: starting a new RFP response from scratch. Run once per RFP. Safe to re-run — skips files that already exist.

### Steps

#### 1. Ask for the RFP name — STOP and wait for the answer

Ask this question first and **do not proceed until the user answers**:

> "What's the name of this RFP? (e.g. 'Acme Retail 2026', 'Saint-Gobain Commerce Platform')
> I'll use it to name the working folder for this response."

**Wait for the user's reply.**

Once the user replies:
1. Slugify the name: lowercase, spaces and special characters replaced with hyphens (e.g. `acme-retail-2026`)
2. Use `<rfp-slug>` as the root folder for everything in this RFP — all files and subfolders live inside it
3. Also write the original name into the `rfp_title:` field of `RFP_CONFIG.md`
4. Continue to step 2

#### 2. Check what already exists

```bash
ls <rfp-slug>/ 2>/dev/null
```

If `<rfp-slug>/` already exists, tell the user and skip creating anything that's already there. Never overwrite.

#### 3. Create RFP folder structure

Create the following (skip anything that already exists):

```
<rfp-slug>/
  RFP_CONFIG.md    ← configuration file for this RFP
  source/          ← drop the customer's RFP document(s) here
  references/      ← past RFP responses used as reference (created in step 5 if needed)
  analysis/        ← auto-generated by 'analyze' mode
  response/        ← auto-generated by 'generate' mode
```

Create `<rfp-slug>/RFP_CONFIG.md` from [rfp-config-template.md](./references/rfp-config-template.md), with `rfp_title:` pre-filled from the name given in step 1.

#### 4. Ask where the RFP document lives — STOP and wait for the answer

Ask this question and **do not proceed until the user answers**:

> "Where is the customer's RFP document? I'll set the `source:` field in `RFP_CONFIG.md` for you:
>
> - **Google Drive link** — paste a `drive.google.com` or `docs.google.com` URL (file or folder)
> - **Local path** — give me a file or folder path (e.g. `~/Downloads/acme-rfp.pdf`)
> - **Already in `<rfp-slug>/source/`** — just tell me and I'll scan that folder automatically
> - **Paste inline** — paste the RFP content directly here"

**Wait for the user's reply.**

Once the user replies:
1. Write their answer verbatim into the `source:` field of `<rfp-slug>/RFP_CONFIG.md`
2. Continue to step 5

#### 5. Ask for reference RFP responses — STOP and wait for the answer

Ask this question and **do not proceed until the user answers**:

> "Do you have previous RFP responses to use as references — for tone, structure, or reusable content?
>
> - **Google Drive link** — paste one or more `drive.google.com` or `docs.google.com` URLs (files or folders)
> - **Local path** — give me a file or folder path (e.g. `~/RFPs/past-responses/`)
> - **Already in `<rfp-slug>/references/`** — just tell me and I'll scan that folder automatically
> - **None** — skip this step"

**Wait for the user's reply.**

Once the user replies:
- If they provided sources: write each entry into the `references:` list in `<rfp-slug>/RFP_CONFIG.md`. Create `<rfp-slug>/references/` if it doesn't exist.
- If they said none or skipped: leave `references:` empty in `RFP_CONFIG.md`. Do not create the folder.

#### 6. Report and hand off

Tell the user:
- The folder created: `<rfp-slug>/`
- Which files were created inside it
- What `source:` was set to
- How many reference documents were registered (or that none were added)
- Next step: fill in the rest of `<rfp-slug>/RFP_CONFIG.md` (customer details, company profile, team), then run `/commercetools-rfp analyze`

## Mode: analyze

**When**: the RFP folder is set up and `RFP_CONFIG.md` is filled in.

### Steps

#### 1. Locate the RFP folder and read configuration

Scan the current directory for subfolders containing `RFP_CONFIG.md`:

```bash
find . -maxdepth 2 -name "RFP_CONFIG.md" 2>/dev/null
```

- If exactly one is found, use that folder as `<rfp-slug>/`. No need to ask.
- If multiple are found, ask: "Which RFP are you working on?" and list the folder names.
- If none is found, ask: "I couldn't find an `RFP_CONFIG.md`. Run `/commercetools-rfp init` first, or give me the path to your RFP folder."

Read `<rfp-slug>/RFP_CONFIG.md` and extract:
- `rfp_title:` — used to label the analysis report
- `source:` path to the RFP document(s)
- `references:` list of past RFP response sources (may be empty)
- `company_name:` of the responder
- `product:` being offered
- `capabilities:` list

If `source:` is empty, ask inline:
> "Where is the RFP document? Give me a file path, a Google Drive link, or paste the content here."

#### 1b. Load reference RFP responses (if any)

If `references:` is non-empty in `RFP_CONFIG.md`, load each entry using the same source-type logic as step 2 (Google Drive URL, local path, or `RFP/references/` folder scan). Read them all before proceeding.

Use the reference documents to:
- Learn the **tone and voice** used in past winning responses
- Identify **reusable content** (company boilerplate, standard capability descriptions, case study write-ups)
- Understand **how gaps were handled** in previous responses
- Note **section structures or formats** that worked well

Keep a mental summary of what the references provide — it will inform scoring notes and the generate step.

If a reference source is a Google Drive URL, apply the same fetch logic as step 2 (Google Drive section).
If references point to `RFP/references/`, resolve to `<rfp-slug>/references/`.

#### 2. Read the RFP document

Detect the source type from the `source:` value and load accordingly:

- **Google Drive URL** — `source:` contains `drive.google.com` or `docs.google.com`:
  1. Extract the file ID from the URL:
     - `https://drive.google.com/file/d/{FILE_ID}/view` → `{FILE_ID}`
     - `https://docs.google.com/document/d/{FILE_ID}/edit` → `{FILE_ID}`
     - `https://drive.google.com/open?id={FILE_ID}` → `{FILE_ID}`
  2. Call `mcp__claude_ai_Google_Drive__get_file_metadata` with the file ID to confirm access and get the file name and MIME type.
  3. If the file is a Google Doc (`application/vnd.google-apps.document`), call `mcp__claude_ai_Google_Drive__read_file_content` with `export_format: "markdown"` to get the content as Markdown.
  4. If the file is a PDF, DOCX, or other binary, call `mcp__claude_ai_Google_Drive__download_file_content` to retrieve its text content.
  5. If access is denied or the file doesn't exist, stop and tell the user: "I couldn't access that Google Drive file. Make sure the file is shared with your Google account connected to Claude, then try again."

- **Google Drive folder URL** — URL contains `/folders/`:
  1. Extract the folder ID from `https://drive.google.com/drive/folders/{FOLDER_ID}`.
  2. Call `mcp__claude_ai_Google_Drive__search_files` with `query: "'{FOLDER_ID}' in parents"` to list all files in the folder.
  3. Read each file using the same logic as above (Google Doc → `read_file_content`; binary → `download_file_content`).
  4. Concatenate all file contents, labelling each section with the file name.

- **Local file path** (`source: RFP/source/rfp.pdf` or `~/Downloads/...`) → read with available file tools
- **Local folder** (`source: RFP/source/` or `<rfp-slug>/source/`) → read all `.pdf`, `.docx`, `.md`, `.txt` files found there
- **Inline** → use content pasted by the user

If the source is empty or unreadable, stop and ask the user to check the path or sharing permissions.

#### 3. Extract requirements

Parse the RFP and identify all stated requirements. Group them into categories:

| Category | Description |
|---|---|
| **Functional** | Features and capabilities the solution must provide |
| **Technical** | Architecture, integration, security, performance constraints |
| **Commercial** | Pricing structure, contract terms, licensing model |
| **Compliance** | Regulatory, data residency, certifications required |
| **Operational** | SLA, support model, onboarding, training |
| **Timeline** | Deadlines, milestones, go-live expectations |
| **Evaluation** | Explicit scoring criteria or decision factors stated in the RFP |

For each requirement, record:
- **ID**: REQ-001, REQ-002, …
- **Category**: one of the above
- **Statement**: the exact or paraphrased requirement text
- **Priority signal**: mandatory / preferred / nice-to-have (infer from language: "must", "shall", "should", "may")
- **CT fit**: ✅ Full match / ⚠️ Partial / ❌ Gap / ❓ Unknown (fill during scoring step)

Number requirements sequentially, not per category.

#### 4. Score requirements against capabilities

For each requirement, check it against `RFP_CONFIG.md` capabilities and known commercetools platform features.

**Before writing any CT capability claim**, query the CT docs MCP (`commercetools-documentation-search`) to verify the feature exists, its scope, and any limitations. Never rely on training data for CT specifics — the platform evolves and incorrect claims in an RFP response are a sales liability.

Score:
- ✅ **Full match**: CT natively supports this, no customisation needed
- ⚠️ **Partial**: CT supports it with configuration, a Connect application, or an integration
- ❌ **Gap**: CT does not support this natively; would require significant custom development or a third-party tool
- ❓ **Unknown**: more information needed from the customer or internal team

#### 5. Identify risks and differentiators

**Risks** — requirements where CT fit is ⚠️ or ❌:
- Describe what the gap is
- Describe the workaround or alternative
- Estimate effort if ❌ (high / medium / low custom dev)

**Differentiators** — requirements where CT excels beyond what the customer asked:
- List capabilities CT provides that the RFP didn't ask for but would matter to the customer (API-first, composable, multi-region, etc.)

#### 6. Generate analysis report

Create `<rfp-slug>/analysis/requirements-analysis.md` using the template in [rfp-analysis-template.md](./references/rfp-analysis-template.md).

The report must include:
- RFP metadata (customer, deadline, evaluation date if stated)
- Requirements table (ID, category, statement, priority, CT fit)
- Risk register (⚠️ and ❌ requirements, each with mitigation)
- Differentiators section
- Recommended response strategy (what to lead with, what to handle carefully)
- Open questions for the customer or internal team

#### 7. Report

Tell the user:
- Total requirements found (count by category)
- Coverage: how many ✅ / ⚠️ / ❌ / ❓
- Top 3 risks
- Top 3 differentiators
- Next step: review `<rfp-slug>/analysis/requirements-analysis.md`, then run `/commercetools-rfp generate`

## Mode: generate

**When**: `RFP/analysis/requirements-analysis.md` is reviewed and approved.

### Steps

#### 1. Read all inputs

Locate `<rfp-slug>/` using the same folder-detection logic as `analyze` step 1 (scan for `RFP_CONFIG.md`, ask if ambiguous).

```bash
cat <rfp-slug>/RFP_CONFIG.md
cat <rfp-slug>/analysis/requirements-analysis.md
```

Also re-read the original RFP source to catch tone, formatting preferences, and any instructions about the response format the customer specified.

If `references:` is non-empty in `RFP_CONFIG.md` and the references were not already loaded in `analyze`, load them now using the same source-type logic (Google Drive URL, local path, or folder scan). Use them to:
- Mirror the **tone and register** of past winning responses
- Reuse **approved boilerplate** (company description, standard capability paragraphs, case study write-ups) verbatim where appropriate — don't rewrite what already worked
- Adapt **section structures or argument patterns** that were effective previously
- Apply **gap-handling language** that was accepted in past responses

#### 2. Determine response format

Check if the customer's RFP specifies a required response format (template, section order, page limit, naming conventions). If yes, follow it exactly. If no format is specified, use the default structure below.

**Ask the user one question before proceeding:**
> "Does the customer require a specific response format or template?
> - If yes, share it or describe the required structure
> - If no, I'll use the standard proposal format"

#### 3. Generate the response document

Create `<rfp-slug>/response/proposal-<customer-name>.md` using the template in [rfp-response-template.md](./references/rfp-response-template.md).

The document must include these sections (adapt order to customer format if required):

**Cover page**
- Responder company, contact, date, RFP reference number
- Confidentiality notice

**Executive Summary** (1 page max)
- Who you are, what you're proposing, why you're the right fit
- Top 3 reasons to choose your solution for this customer's specific context
- Never generic — reference the customer's stated goals from the RFP directly

**Company & Solution Overview**
- Company profile (from `RFP_CONFIG.md`)
- Product overview: what CT is, its architecture philosophy, key differentiators
- Relevant customer references / case studies (from `RFP_CONFIG.md`)

**Requirements Response Table**
- One row per requirement (REQ-001 … REQ-NNN)
- Columns: ID | Requirement | Our Response | CT Fit | Notes
- For ✅: state clearly how CT addresses it, name the feature/API
- For ⚠️: describe the configuration or partner solution
- For ❌: acknowledge the gap, propose the alternative, be direct
- Never omit a requirement — gaps must be addressed, not hidden

**Solution Architecture** (if technical requirements are significant)
- High-level architecture diagram (as ASCII or Mermaid code block)
- Key integration points
- Data flow for the customer's main use cases
- Security and compliance approach

**Implementation Plan**
- Phases and milestones
- Timeline estimate (in weeks from contract signature)
- Roles and responsibilities
- Onboarding and training approach

**Pricing** (if `RFP_CONFIG.md` includes pricing tiers)
- Model overview (subscription, usage-based, etc.)
- Indicative pricing table
- What's included / excluded
- Commercial terms summary

**Team**
- Named contacts from `RFP_CONFIG.md`
- Roles in the engagement
- Relevant experience for this deal

**References & Case Studies**
- 2–3 customer references matching the RFP customer's industry or use case
- Brief case study for each: challenge → solution → outcome

**Appendices** (as needed)
- Security questionnaire responses
- Compliance certifications
- SLA details
- Glossary

#### 4. Validate coverage

After generating the document, check every requirement from `requirements-analysis.md` is addressed in the requirements response table. Flag any missing as a `[TODO]` placeholder rather than silently omitting them.

Count and report:
- Requirements addressed: N / total
- `[TODO]` placeholders: list them

#### 5. Report

Tell the user:
- File created: `<rfp-slug>/response/proposal-<customer-name>.md`
- Requirements coverage: N/total
- Any `[TODO]` items that need manual input (pricing, specific case study details, etc.)
- Recommended next step: run `/commercetools-rfp review` or share the document for internal review

## Mode: review

**When**: the proposal draft is ready for final check before sending.

### Steps

#### 1. Read all files

Locate `<rfp-slug>/` using the same folder-detection logic as `analyze` step 1.

```bash
cat <rfp-slug>/RFP_CONFIG.md
cat <rfp-slug>/analysis/requirements-analysis.md
cat <rfp-slug>/response/proposal-*.md
```

Also re-read the original RFP source.

#### 2. Check coverage

Build a checklist:

- [ ] Every requirement from `requirements-analysis.md` has a row in the response table
- [ ] No requirement marked ❌ is silently skipped — gaps must be acknowledged
- [ ] No `[TODO]` placeholder remains in the final document
- [ ] Every claim about CT capabilities has been verified (no unsupported assertions)
- [ ] All named case studies are real (from `RFP_CONFIG.md`, not invented)
- [ ] Pricing figures match `RFP_CONFIG.md` — no numbers made up
- [ ] Named team members match `RFP_CONFIG.md`
- [ ] Executive summary references the customer's specific goals (not generic)
- [ ] The document follows the format/structure the customer requested (if specified)
- [ ] No confidential information from other customers is included

#### 3. Check tone and quality

- [ ] Executive summary is ≤ 1 page
- [ ] No vague phrases like "world-class", "best-in-class", "cutting-edge" without evidence
- [ ] Technical claims are specific (endpoint names, API types, architecture patterns)
- [ ] Timeline estimates are marked as indicative, not guaranteed
- [ ] Pricing includes all relevant caveats (indicative, subject to scoping, etc.)

#### 4. Flag issues

For each failed checklist item, output:
```
⚠️ [ISSUE] <what's wrong> — <what to fix>
```

For each passed item, output:
```
✅ [OK] <what was checked>
```

#### 5. Report

Summarise:
- Total issues found (count of ⚠️)
- Severity: Blockers (must fix before sending) vs Improvements (recommended)
- List blocker issues with suggested fixes
- If zero blockers: confirm the document is ready to send

## Key Rules

**CT capability claims must be verified.** Before writing any capability claim in the analysis or response, query the CT docs MCP. An incorrect claim in a sent proposal is a contractual and trust risk.

**Never omit a requirement.** If CT can't do something, say so and propose the path forward. Customers find gaps themselves — it's better to be upfront than to discover them during implementation.

**Case studies must be real.** Only use case studies from `RFP_CONFIG.md`. Never invent customer references or fabricate outcomes.

**Pricing must be marked indicative.** Unless you have an approved quote, all pricing in the response must be clearly marked as indicative and subject to final scoping.

**Executive summary is customer-specific.** Read the RFP's stated goals and write the executive summary to those goals. A generic summary is a signal that you didn't read the RFP.

**The requirements table is the core of the response.** Every other section supports it. If the table is incomplete or wrong, the proposal fails.

---

## Anti-Patterns

| Anti-pattern | Correct approach |
|---|---|
| Omitting ❌ requirements from the response | Acknowledge every gap; propose the alternative |
| Using generic executive summaries | Reference the customer's specific goals and context |
| Inventing case studies | Only use references from `RFP_CONFIG.md` |
| Writing CT capability claims without verifying | Always query the CT docs MCP before claiming a feature |
| Leaving `[TODO]` in the sent document | Review mode must clear all placeholders before send |
| Pricing without caveats | Always mark as indicative, subject to scoping |
| Skipping the review mode | Run review before sending — it catches coverage gaps |
| Using vague superlatives | Back every claim with a specific feature, metric, or reference |
